# Интерактивная рабочая сессия — исходящая сеть

**Обновлено 2026-08-08 (сессия `recurring-people-photo-and-bio-backfill`): доступ шире, чем
описывала предыдущая версия этой заметки — перепроверяйте перед тем, как заранее списывать
фото со счетов.** Не считайте это состояние постоянным: egress через прокси менялся дважды в
течение одного дня, перепроверьте актуальность при следующем обогащении, если что-то не
сходится с описанным здесь.

Интерактивная (не bot/, не Cloudflare Worker) рабочая сессия — там, где идёт человеческое
обогащение данных с помощью Bash/WebFetch/агентов-исследователей — идёт через организационный
egress-прокси (`$https_proxy`). Состояние на 2026-08-08 (вторая проверка в тот же день):
`ru.wikipedia.org`, `upload.wikimedia.org`, `mosconsv.ru`, `belcanto.ru`, `mariinsky.ru`,
`zaryadyehall.ru`, `stanmuz.ru` — все отвечают нормально (`curl`/`WebFetch` работают, можно
скачивать страницы и изображения). Это шире, чем более ранняя проверка того же дня, которая
нашла блокировку «политикой» (403 `policy denial` от `$HTTPS_PROXY/__agentproxy/status`) для
всех внешних доменов без исключения — доступ, видимо, менялся в течение дня.

**Известное исключение: `bolshoi.ru` (и `www.bolshoi.ru`) не отвечает** — HTTPS CONNECT через
прокси либо зависает до таймаута, либо возвращает `502 Bad Gateway`, воспроизводимо в нескольких
попытках; `WebFetch` к тем же URL — `Socket is closed`. Открытым остаётся вопрос, специфическая
ли это блокировка домена или проблема самого bolshoi.ru — на практике разницы нет: страницы
`bolshoi.ru/persons/...` (основной источник био/фото для артистов Большого театра, самой
частой категории в бэклоге recurring-people) физически недостижимы из этой сессии, а прочие
проверенные домены — достижимы. Это доменно-специфичный факт, а не общий вывод «весь внешний
egress закрыт» — не экстраполировать на другие домены без проверки.

**Практические следствия:**
- Перед тем как писать research-агентам, что фото недостижимо, **проверьте конкретный домен
  источника** (`curl -s -o /dev/null -w '%{http_code}' --max-time 15 <url>` или один пробный
  `WebFetch`) — не полагайтесь на предыдущую версию этой заметки как на актуальный статус.
- Для `bolshoi.ru` конкретно: фото по-прежнему нельзя скачать напрямую в этой сессии — оставлять
  поле **Фото:** пустым, указывать страницу-источник в **Источник:**, фиксировать причину в
  `## History` профиля, как раньше.
- Для доменов из проверенного выше списка (mariinsky.ru, mosconsv.ru, belcanto.ru,
  zaryadyehall.ru, stanmuz.ru, wikipedia/wikimedia) — `helpers/fetch_person_photo.py` работает
  как обычно, фото скачивать и кадрировать можно.
- `WebSearch` (сниппеты через поисковый бэкенд) по-прежнему полезен как наводка, но не заменяет
  чтение первоисточника, когда первоисточник достижим.
- Не пытаться обходить фактическую блокировку конкретного домена (см. `/root/.ccr/README.md`:
  «do not retry or route around it» для 403/407 от egress-прокси) — если это действительно нужно
  для достижения bolshoi.ru, это вопрос к администратору окружения, не к инструментам сессии;
  для всего остального доступ, по всей видимости, уже широкий.

**Не путать с ботом:** `bot/worker.js` работает как Cloudflare Worker в другой сети (без этого
прокси) и уже сегодня напрямую обращается к mariinsky.ru/mosconsv.ru/zaryadyehall.ru/stanmuz.ru/
vnutri.space для афиш — это ограничение относится только к интерактивным рабочим сессиям, не к
продакшен-боту.
